# GitHub 同步建议

本知识库不建议把每一次爬取动作都实时推送到 GitHub。更稳妥的做法是按“代码与规则实时可追踪，数据按批次快照”的方式管理。

## 一、建议同步到 GitHub 的内容

适合纳入 GitHub：

- `scripts/`：采集、评测、日志、后续检索与 RAG 脚本
- `00_说明/`：建设说明、来源规则、评测说明、同步建议
- `02_元数据/`：来源清单、地区覆盖清单、问题评测表、人工核验表、待采集链接
- `04_标签与权重/`：标签体系、权重规则
- 关键实验结果摘要：例如 Top3 命中率、元数据核验结论

谨慎纳入 GitHub：

- `01_原始资料/`：原始网页、PDF、Word 可能数量大，也可能涉及第三方版权或转载内容
- `03_处理后文本/`：从网页或文件抽取出的全文文本可能很大，也可能包含第三方内容
- `05_输出成果/`：候选链接和评测结果可以保留，批量中间文件建议按需要选择
- `06_实验日志/`：建议保留，但如果出现账号、Cookie、内部路径或敏感信息，需要先清理

## 二、推荐同步频率

不建议：

- 每采一条资料就推送
- 每次运行脚本都自动推送
- 把大批量原始文件直接推到公开仓库

建议：

- 修改脚本、字段模板、来源清单后提交一次
- 每完成一轮实验后提交一次
- 每天或每周保存一次元数据快照
- 大批量原始文件先放本地或对象存储，GitHub 只保存索引和清单

## 三、仓库公开性建议

第一阶段建议使用私有仓库。

原因：

- 当前还在探索字段、脚本和来源边界
- 公众号、咨询机构资料不适合直接公开全文
- 实验日志可能包含本地路径和操作细节
- 后续可能接入 API Key、Cookie 或内部资料，需要提前隔离

等字段稳定、来源边界清晰后，可以考虑拆成两个仓库：

- 公开仓库：脚本、模板、空白表结构、通用说明
- 私有仓库：实际数据、原始资料、实验日志、评测结果

## 四、建议的提交节奏

当前阶段可以采用：

```text
脚本或模板有变化 -> 提交
来源清单新增一批 -> 提交
采集一批核心资料 -> 提交元数据快照
完成一次评测实验 -> 提交评测结果和实验日志
原始资料文件 -> 暂不默认提交
```

## 五、结论

这个知识库需要 GitHub 做版本管理，但不需要实时推送全部数据。

更合适的策略是：

```text
代码、模板、规则、来源清单：及时提交
元数据和评测结果：按实验批次提交
原始资料和处理后全文：默认本地保存，必要时用私有仓库或 Git LFS 管理
```
